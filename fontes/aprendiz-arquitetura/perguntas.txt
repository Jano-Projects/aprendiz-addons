P: como o aprendiz funciona por dentro
P: qual a arquitetura do aprendiz
P: quais são as camadas do aprendiz
R: O Aprendiz tem **três camadas** que conversam por interfaces simples:
```
┌─────────────────────────────────────────────────────┐
│ Interface (aprendiz/web/)   HTML + CSS + JS puros    │
│        │  fetch() em JSON                            │
├────────┼────────────────────────────────────────────┤
│ API (aprendiz/api/servidor.py)  FastAPI, 127.0.0.1   │
│        │                                             │
├────────┼────────────────────────────────────────────┤
│ Núcleo (aprendiz/core/assistente.py)                 │
│   ├── linguagem/  normaliza e interpreta o texto     │
│   ├── algoritmos/ busca e monta a resposta           │
│   └── memoria/    SQLite: um arquivo, toda a memória │
└─────────────────────────────────────────────────────┘
```
E o `aplicativo/desktop.py` amarra tudo: sobe a API numa thread e abre a interface numa janela.
Cada camada só conhece a de baixo: a interface não sabe nada de SQLite; o banco não sabe nada de linguagem. Por isso cada peça pode ser testada sozinha.

F: caminho-mensagem
A: caminho de uma mensagem, pipeline, etapas
Q: porque | cada mensagem passa por etapas em ordem, e cada uma registra o que fez no Monitor
Q: consequencia | na 2.4, as etapas chegam à interface ao vivo | -> monitor
Q: consequencia | na 2.0 entram os padrões de frase, a teia e a resposta Trabalhada | -> aprendiz-algoritmos:teia
P: qual o caminho de uma mensagem no aprendiz
P: o que acontece quando eu mando uma mensagem no aprendiz
P: o que é o pipeline do aprendiz
P: como funciona o pipeline
P: pipeline do aprendiz
R: Do Enter até a resposta na tela:
1. **Interface** (`web/app.js`, função `enviar`): faz `POST /api/chat/fluxo` (na 2.4; antes, `POST /api/chat`) com a mensagem e os algoritmos escolhidos.
2. **API** (`api/servidor.py`, rota `chat`): valida o JSON e chama `Assistente.responder()`.
3. **Núcleo** (`core/assistente.py`): grava a mensagem e roda o **pipeline** (`_pipeline`):
   - normalização (`Linguagem.processar`);
   - ensino explícito ("aprenda que…", "pergunta: … resposta: …");
   - revisão de texto (com addon de norma) e dicionário (verbetes);
   - interpretação: intenção (Naive Bayes) e entidades (regex);
   - intenção social ("oi", "obrigado") → resposta pronta;
   - compreensão (com addon de compreensão);
   - **busca** com o algoritmo escolhido e o **limiar**;
   - nada acima do limiar → **modo estrito** ("ainda não fui ensinado");
   - **resposta** com o algoritmo escolhido (Direta ou Extrativa).
4. Cada etapa é cronometrada (classe `Etapas`); tudo vira `meta.explicacao`, gravado com a resposta.
5. A API devolve o JSON; a interface mostra o texto (com o mini-Markdown) e entrega a explicação ao **Monitor**. Na 2.4, cada etapa já chega ao Monitor assim que termina (NDJSON).
**Na 2.0:** o caminho ganhou três etapas: **padrões de frase** antes da busca, as **regras do assunto** depois dela e a **teia de porquês** antes de montar a resposta. Veja o `docs/referencia/arquitetura.md`.

F: decisoes
A: decisões de projeto, por que offline, por que sqlite
Q: porque | rodar em máquina fraca, offline e sem dependências pesadas guiou cada escolha
P: quais as decisões de projeto do aprendiz
P: por que o aprendiz usa interface web
P: por que o aprendiz não usa inteligência artificial
R: As escolhas principais e o porquê (estão em `docs/referencia/arquitetura.md`):
- **Servidor web local em vez de Tkinter ou Qt:** HTML/CSS é o jeito mais acessível de fazer uma interface bonita, e quem estuda abre o DevTools e vê cada requisição.
- **SQLite:** um arquivo só, sem servidor, já vem no Python, com busca textual (FTS5) e BM25 prontos. Copiar o arquivo é copiar toda a memória.
- **Sem modelo de linguagem:** técnicas clássicas de PLN resolvem bem "achar o que foi ensinado", rodam em milissegundos e cabem em qualquer máquina. E cada resposta pode ser explicada com números.
- **Banco separado da linguagem:** o `Banco` só lê e grava; a `Linguagem` entende texto; o `Assistente` decide.
- **Algoritmos como plugins (padrão Strategy):** todos os de busca têm `buscar()`, todos os de resposta têm `responder()`; o decorador `@registrar` os coloca no seletor.
- **Addons só de dados:** nada que um addon traga é executado como código.
- **Nada da internet na interface:** nem fontes, nem ícones, nem bibliotecas externas.

R: `aprendiz/aplicativo/config.py` guarda valores que mudam pouco:
- `NOME_APP`, `VERSAO`, `PORTA_PADRAO = 8765`;

F: desktop
A: desktop.py, janela, abrir o app
Q: porque | sobe a API numa thread e abre a interface numa janela | -> servidor
P: o que faz o arquivo desktop.py do aprendiz
P: como o aprendiz abre a janela
P: pra que serve o desktop.py
P: o que faz o desktop.py
R: `aprendiz/aplicativo/desktop.py` transforma um servidor web num "app de desktop":
1. `escolher_porta()`: tenta a 8765; se estiver ocupada, pede uma livre ao sistema (porta 0);
2. `iniciar_servidor()`: cria a aplicação (`criar_app()`) e roda o **Uvicorn** numa **thread** separada, esperando até 20 s que ele fique pronto;
3. abre a interface, nesta ordem:
   - janela nativa com o **pywebview**, se instalado (no Windows usa o Edge WebView2);
   - um **Chromium em modo aplicativo** (Chrome, Chromium, Edge, Brave), sem barra de endereço e com perfil separado;
   - o navegador padrão, numa aba (sempre funciona);
4. encerra sozinho: a página manda um **sinal de vida** a cada 10 s (`POST /api/sinal`); se os sinais param por 90 s (janela fechada), o servidor sai. Isso evita processos esquecidos, principalmente no executável do Windows, que não tem console.
O `main()` lê as opções com `argparse` (`--modo`, `--porta`).

F: servidor
A: servidor.py, api, fastapi, rotas
Q: porque | expõe o núcleo em rotas HTTP só no próprio computador | -> prog-vocabulario:api
P: o que faz o arquivo servidor.py do aprendiz
P: quais são as rotas da api do aprendiz
P: quais rotas a api tem

R: `aprendiz/api/servidor.py` cria a aplicação **FastAPI** na função `criar_app(caminho_banco)`, que monta o `Banco` e o `Assistente` e declara as rotas. Ela só escuta em **127.0.0.1**. As rotas principais:
- `GET /`: a interface; `/static/...`: os arquivos de `web/`;
- `GET /api/status`, `GET /api/algoritmos`;
- `POST /api/chat` (perguntar), `POST /api/corrigir`;
- `GET/POST/PUT/DELETE /api/conhecimentos...` (a base), `POST /api/importar` (.txt/.md);
- `GET /api/conversas`, mensagens, renomear, apagar;
- `/api/addons...`: listar, inspecionar sem instalar, instalar, ativar/desativar, remover, grupos;
- `/api/exportar...`: prévia, recomendação e geração do addon;
- `/api/configuracoes...`, `/api/linguagem...`;
- `POST /api/revisar`, `GET /api/normas` (revisão de texto);
- `POST /api/resetar` (exige o texto "RESETAR"; faz backup antes), `POST /api/sinal`, `POST /api/loja-oficial`.
Cada pedido com corpo tem um modelo **Pydantic** (`PedidoChat`, `PedidoAddon`…), que valida o JSON antes da função rodar. A lista completa está na docstring do arquivo e em `/docs`.

F: assistente
A: assistente.py, núcleo, responder
Q: porque | é onde o pipeline acontece, chamando linguagem, busca, teia e resposta | -> caminho-mensagem
P: o que faz o arquivo assistente.py do aprendiz
P: o que é a classe assistente
P: o que faz o assistente.py
R: `aprendiz/core/assistente.py` é o **coração**: a classe `Assistente` junta linguagem, memória e algoritmos. É o primeiro arquivo da trilha de estudo do README.
O que ela faz:
- `ensinar()` / `importar_texto()`: grava conhecimentos já com o texto de busca (radicais);
- `reindexar()`: recalcula os radicais de toda a base (quando sinônimos, abreviações ou addons de compreensão mudam);
- `responder()` e `_pipeline()`: o caminho de uma mensagem, etapa por etapa;
- `buscar()`: roda o algoritmo de busca, aplica o limiar e a **prioridade do dono** sobre os addons;
- `inspecionar_addon()`, `instalar_addon()`, ativar, remover, grupos e padrão de addons;
- `corrigir()`: transforma uma correção do dono num ensinamento;
- `revisar_texto()`: a revisão pela norma de um país.
No começo do arquivo ficam as constantes do pipeline: as expressões regulares do ensino pelo chat (`PADRAO_PAR`, `PADRAO_FATO`, `PADRAO_NOTA`) e os critérios da resposta social (probabilidade mínima 0,45, margem de 2× sobre a segunda intenção, até 6 palavras).

A: pasta core, núcleo do assistente

R: A pasta `aprendiz/core/` é o núcleo do raciocínio (2.5):
- `assistente.py`: o pipeline (veja "o que faz o arquivo assistente.py");
- `teia.py`: o caminho de porquês a partir do conhecimento achado;
- `padroes.py`: o sentido pela estrutura da frase ("quantos * cada *");
- `expressao.py`: o jeito humano de dizer cada parte da resposta;
- `monitor.py`: a ficha técnica do modelo e a memória do processo, para o Monitor.
Os motores que os addons de língua ligam ficam em `aprendiz/capacidades/`:
- `dicionario.py`: os verbetes nos dois sentidos ("o que significa kota?" e "como se diz dinheiro em Angola?");
- `compreensao.py`: tipo da pergunta, perguntas sobre o próprio app, pedidos fora de alcance, busca por sentido e recomendação de addon;
- `dialogo.py`: reações à resposta anterior, continuações e atos de fala;
- `revisao.py`: revisão de textos pela norma de um país.
E as peças de addons ficam em `aprendiz/addons/`: `recomendacao.py` (testa os algoritmos com o conteúdo de um addon) e `exportacao.py` (transforma o que o dono ensinou num addon).
Regra importante: os motores ficam no app; os addons só trazem **dados**.

F: pasta-linguagem
A: pasta linguagem, normalizador, léxico
Q: parte-de | prepara o texto, e na 2.0 também normaliza números e contas | -> aprendiz-algoritmos:normalizacao
P: o que tem na pasta linguagem do aprendiz
P: o que fazem normalizador.py stemmer.py intencoes.py
P: o que faz o normalizador.py
P: o que faz o stemmer.py

R: A pasta `aprendiz/linguagem/` é o processamento de linguagem natural, sem redes neurais:
- `normalizador.py`: transforma a mensagem crua em radicais: minúsculas, sem acento, tokens, abreviações, correção de digitação, sinônimos, stopwords e radicais. Guarda todas as etapas num `TextoProcessado`. A classe `Linguagem` mantém as tabelas em memória;
- `stemmer.py`: o **radicalizador** (RSLP simplificado): "ensinando" → "ensin";
- `intencoes.py`: o classificador **Naive Bayes** escrito do zero (saudação, despedida, agradecimento, ajuda, pergunta, ensinar);
- `entidades.py`: extrai e-mail, valor em reais, data, horário, telefone e número com **regex**;
- `lexico.py`: lemas e vetores de palavras trazidos pelos addons de compreensão, consultados no SQLite com cache.
**Na 2.0:** entrou `numeros.py`, que deixa "2+2", "dois mais dois" e "2 mais dois" numa forma só.

F: pasta-algoritmos
A: pasta algoritmos, busca e resposta
Q: parte-de | cada algoritmo é um arquivo registrado; na 2.0 entrou a resposta Trabalhada | -> aprendiz-algoritmos:trabalhada

R: A pasta `aprendiz/algoritmos/` é o **seletor**:
- `base.py`: os contratos: `AlgoritmoBusca` e `AlgoritmoResposta` (classes abstratas), as classes de dados `Candidato`, `RespostaGerada` e `ContextoBusca`, o decorador `@registrar` e os registros `BUSCAS` e `RESPOSTAS`;
- `busca/bm25.py`: BM25 calculado pelo FTS5 do SQLite (o padrão, o mais leve);
- `busca/tfidf.py`: TF-IDF + cosseno, em Python puro (o mais didático);
- `busca/fuzzy.py`: semelhança de letras com o RapidFuzz (tolera erros de digitação);

- `resposta/direta.py`: devolve o conhecimento como foi ensinado;
- `resposta/extrativa.py`: escolhe as frases mais relevantes de vários conhecimentos (TextRank).
A **ordem dos imports** nos `__init__.py` de `busca/` e `resposta/` define a ordem no seletor da interface.
**Na 2.0:** entrou `resposta/trabalhada.py`, a resposta que explica os porquês.

A: pasta memoria, banco, sqlite

R: A pasta `aprendiz/memoria/` cuida da persistência:
- `banco.py`: a classe `Banco`, a **única** que fala SQL. Cria o esquema, faz as **migrações** de bancos antigos, mantém o índice FTS5, guarda conhecimentos, linguagem, addons, configurações e conversas, faz backup (`Connection.backup`) e o reset. Usa uma trava (`RLock`) para as várias threads do servidor não escreverem ao mesmo tempo, e dois contadores (`versao_conhecimento`, `versao_linguagem`) que avisam os caches quando algo mudou;
- `sementes.py`: os dados iniciais do banco de linguagem, gravados na primeira execução: abreviações (`vc → voce`), sinônimos (`automovel → carro`), stopwords, frases de exemplo de cada intenção e as respostas sociais prontas. Tudo sem acento e em minúsculas, como o normalizador deixa o texto.

F: tabelas
A: tabelas do banco, esquema, conhecimentos
Q: porque | cada tipo de dado tem a sua tabela, e na 2.0 os conhecimentos ganharam a coluna teia | -> pasta-memoria

R: O `aprendiz.db` tem estas tabelas (o esquema está no topo de `memoria/banco.py`):

F: addons-py
A: pacote.py, addons.py, pacote .aprendiz, validar addon
Q: porque | lê o pacote com cuidado, valida tudo e só então grava | -> addons-arquitetura
P: o que faz o arquivo addons.py
P: como o aprendiz lê um arquivo .aprendiz
P: o que faz o addons.py
P: o que faz o pacote.py
P: o que faz o arquivo pacote.py
R: `aprendiz/addons/pacote.py` (o antigo `addons.py`, até a 2.4) é o **formato `.aprendiz`**: um ZIP com JSON dentro. Ele trata todo addon como **dado não confiável**:
- `ler_pacote(bytes)`: abre o ZIP **sem extrair nada para o disco**, lê só os nomes conhecidos (`manifesto.json`, `conhecimentos.json`, `linguagem.json`…), confere limites (50 MB compactado, 200 MB descompactado, 100 mil conhecimentos, 20 mil caracteres cada), valida cada campo e remove caracteres de controle;
- `validar_manifesto`, `validar_conhecimentos`, `validar_linguagem`…: uma função por parte;
- `classificacao_de()`: deduz o que o addon mexe (`memoria`, `linguagem`, `parametros`…); a classificação declarada tem de bater com os arquivos;
- `criar_pacote()`: gera um `.aprendiz` válido (usado pela exportação e pelo `ferramentas/criar_addon.py`);
- `chave_de_grupo()`: agrupa addons pela busca e resposta recomendadas;
- `dividir_em_trechos()`: quebra textos longos em pedaços de até 800 caracteres.

F: monitor
A: monitor, painel técnico, pipeline ao vivo, parâmetros, ndjson, fluxo, telemetria
Q: porque | mostra por dentro cada resposta, para quem estuda IA | -> caminho-mensagem
Q: regra | o Monitor só lê dados: nada do que mostra muda a resposta
Q: consequencia | a aba Busca mostra a conta da busca Calibrada sinal por sinal | -> aprendiz-algoritmos:calibrado
P: o que é o monitor do aprendiz
P: como funciona o monitor
P: como o aprendiz mostra o pipeline ao vivo
P: quantos parâmetros o aprendiz tem
P: o que é a rota chat fluxo
R: O **Monitor** (2.4) é o painel à direita do chat, com dois níveis de leitura (**Iniciante** e **Avançado**) e cinco abas:
- **Pipeline:** cada etapa ao vivo, com tempo, início (gráfico de Gantt) e dados; a **câmera lenta** espaça as etapas;
- **Busca:** candidatos, confiança × limiar e, na busca Calibrada, a conta inteira (`z = viés + Σ peso·sinal`, `p = σ(z)`);
- **Modelo:** a ficha técnica, com os **parâmetros** de cada componente: aprendidos, estatísticas da base, pré-treinados e hiperparâmetros;
- **Desempenho:** tempo médio de cada etapa, p90 e memória;
- **Glossário:** os termos técnicos, de *token* a *validação cruzada*.
Como chega ao vivo: `Assistente.responder(..., ouvinte=...)` chama o **ouvinte** a cada etapa marcada (classe `Etapas`). A rota `POST /api/chat/fluxo` roda o Assistente numa thread, põe cada etapa numa `queue.Queue` e envia uma linha JSON por etapa (**NDJSON**, `StreamingResponse`): é o padrão **produtor-consumidor**. A interface lê com `ReadableStream`.
A ficha vem de `GET /api/modelo` (`core/monitor.py`). Com os addons da homologação, são cerca de 1,8 milhão de parâmetros, quase todos pré-treinados (vetores de palavras e lemas); os aprendidos com rótulos são menos de mil.
Detalhes: `docs/estudo/monitor.md`.

F: caches
A: caches, versão do conhecimento, reindexar
Q: porque | contadores de versão dizem quando um cálculo guardado ficou velho, e na 2.0 a teia e os padrões usam os mesmos | -> tabelas
P: como funcionam os caches do aprendiz
P: o que é versao_conhecimento e versao_linguagem
R: Vários pedaços do Aprendiz guardam coisas em memória para não recalcular a cada pergunta: o índice TF-IDF, o índice Fuzzy, o vocabulário do corretor, o classificador de intenções, o índice de verbetes.
Para saber quando recalcular, o `Banco` mantém **dois contadores**: `versao_conhecimento` e `versao_linguagem`, que aumentam a cada alteração. Cada cache guarda a versão com que foi feito e compara antes de usar:
```python
cache = ctx.cache.get(self.nome)
if cache and cache["versao"] == ctx.banco.versao_conhecimento:
    return cache                     # nada mudou: reaproveita
# ... senão, reconstrói e guarda com a versão atual
```
É uma forma barata e simples de **invalidar cache**. Além disso, quando sinônimos, abreviações ou addons de compreensão mudam, os radicais gravados ficam velhos: aí o `Assistente.reindexar()` recalcula o `texto_busca` de toda a base, numa transação só.
**Na 2.0:** a teia usa `versao_conhecimento`, e os padrões e a expressão usam `versao_linguagem`, do mesmo jeito que os índices.

F: addons-arquitetura
A: addons na arquitetura, onde ficam os addons
Q: porque | conhecimentos de addons ficam na mesma tabela, marcados com o addon, e na 2.0 trazem a teia de porquês | -> aprendiz-algoritmos:teia
P: como os addons se encaixam na arquitetura do aprendiz
P: onde ficam os conhecimentos dos addons
R: Um addon não é um "programa à parte": ao instalar, o conteúdo dele vai para as **mesmas tabelas**, marcado com o `addon_id`:
- conhecimentos → tabela `conhecimentos` (com `addon_id`);
- sinônimos, abreviações, stopwords, intenções → `addon_linguagem`;
- parâmetros e personalização → `configuracoes` (com `addon_id`);
- compreensão, vetores, norma → `addon_recursos` e `addon_lexico`.
**Desativar** um addon não apaga nada: a busca filtra os desativados (no próprio SQL do BM25, ou ao montar os índices do TF-IDF e do Fuzzy). **Remover** apaga, numa transação, tudo o que ele trouxe, tabela por tabela (`Banco._apagar_addon`). A instalação é **atômica**: ou entra tudo, ou nada muda. E o que o **dono** ensinou ou configurou sempre tem prioridade sobre os addons.
**Na 2.0:** os conhecimentos de addons podem trazer a **teia de porquês**, que liga fragmentos do mesmo addon ou de outros (`addon:ref`).
