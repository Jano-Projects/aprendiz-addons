A: tipos, integer, text, real, tipo de dado

R: O SQLite tem cinco classes de armazenamento: `INTEGER`, `REAL`, `TEXT`, `BLOB` (bytes) e `NULL`, e é flexível com os tipos (uma coluna INTEGER aceita texto, a não ser em tabelas `STRICT`).
Outros bancos são rígidos e têm mais tipos:
- inteiros: `SMALLINT`, `INTEGER`, `BIGINT`;
- exatos: `NUMERIC(10,2)` / `DECIMAL(10,2)`: **use para dinheiro**;
- reais: `REAL`, `DOUBLE PRECISION` (aproximados; nunca para dinheiro);
- texto: `VARCHAR(n)`, `TEXT`, `CHAR(n)`;
- datas: `DATE`, `TIME`, `TIMESTAMP` (o SQLite guarda datas como texto ISO `'2026-01-10'`);
- `BOOLEAN` (no SQLite, 0 e 1).
No SQLite, para dinheiro, guarde **centavos em INTEGER** (`12050` = R$ 120,50).

F: like
A: like, padrão, texto parecido, curinga
Q: parte-de | o LIKE é uma condição do WHERE: o = só acha o texto exato, o LIKE aceita partes com % e _ | -> where
P: como usar like em sql

P: o que é % e _ no like
R: `LIKE` compara com um **padrão**:
- `%`: qualquer sequência de caracteres (inclusive nenhum);
- `_`: exatamente um caractere.
```sql
SELECT * FROM clientes WHERE nome LIKE 'A%';      -- começa com A
SELECT * FROM clientes WHERE nome LIKE '%Lima';   -- termina com Lima
SELECT * FROM produtos WHERE nome LIKE '%ca%';    -- contém "ca"
SELECT * FROM clientes WHERE uf LIKE 'P_';        -- PE, PR…
```
No SQLite, `LIKE` ignora maiúsculas/minúsculas só nas letras sem acento ('a' = 'A', mas 'é' ≠ 'É'). Um `LIKE '%texto'` não aproveita índice; para busca de texto de verdade, o SQLite tem o FTS5.

N: raiz
A: null, nulo, vazio, sem valor, is null, em branco, valor ausente, campo vazio, não preenchido
Q: definicao | NULL quer dizer valor desconhecido, e não zero nem texto vazio

P: o que é null em sql
P: como verificar se é nulo em sql
P: por que = null não funciona
R: `NULL` significa **desconhecido / sem valor**. Não é zero nem texto vazio.
Qualquer comparação com NULL dá NULL (nem verdadeiro, nem falso), então **`= NULL` nunca encontra nada**. Use:
```sql
SELECT * FROM clientes WHERE cidade IS NULL;
SELECT * FROM clientes WHERE cidade IS NOT NULL;
SELECT nome, COALESCE(cidade, 'não informada') AS cidade FROM clientes;
```
`COALESCE(a, b, …)` devolve o primeiro valor não nulo. Contas com NULL dão NULL (`5 + NULL` é NULL), e as funções de agregação (`SUM`, `AVG`) ignoram os NULL.

R: ```sql
SELECT nome, preco FROM produtos ORDER BY preco DESC LIMIT 3;          -- os 3 mais caros
SELECT nome FROM produtos ORDER BY id LIMIT 2 OFFSET 2;                -- página 2, de 2 em 2
```
Cada banco escreve de um jeito:
- SQLite, PostgreSQL, MySQL: `LIMIT n OFFSET m`;
- SQL Server: `SELECT TOP 3 ...` ou `OFFSET m ROWS FETCH NEXT n ROWS ONLY`;
- Oracle (12c ou mais novo) e o padrão SQL: `FETCH FIRST 3 ROWS ONLY`.
Use sempre com `ORDER BY`, senão "os 3 primeiros" são quaisquer 3. Para páginas muito fundas, `OFFSET` fica lento; a alternativa é continuar de onde parou (`WHERE id > último_id_visto`).

Sem `WHERE`, apaga **todas** as linhas. Confira com um `SELECT` antes, como no `UPDATE`.
As três formas de "apagar":
- `DELETE FROM t WHERE ...`: apaga **linhas**; a tabela continua; pode ser desfeito numa transação;
- `TRUNCATE TABLE t`: esvazia a tabela inteira de uma vez, rápido (não existe no SQLite: lá se usa `DELETE FROM t`);

R: `GROUP BY` junta as linhas com o mesmo valor e aplica a agregação **em cada grupo**:
```sql
SELECT categoria, COUNT(*) AS qtd, AVG(preco) AS preco_medio

```

- Cozinha · 1 · 35.0
- Informática · 4 · 319.75
- Móveis · 2 · 925.0
Regra: toda coluna no `SELECT` que **não** está numa agregação precisa estar no `GROUP BY`. (O SQLite tolera, mas devolve um valor qualquer do grupo; PostgreSQL e outros dão erro.)

F: having
A: having, filtrar grupos, filtro de agregação
Q: porque | os totais só existem depois do GROUP BY, e o WHERE age antes dele | -> group-by
Q: diferente-de | o WHERE filtra linhas antes de agrupar; o HAVING filtra grupos depois | -> where
P: como usar having

P: having
P: por que o where não funciona com count
P: como filtrar pelo resultado do count
P: como filtrar por total ou soma
P: where com count dá erro
R: - `WHERE` filtra **linhas**, antes de agrupar;
- `HAVING` filtra **grupos**, depois de agrupar (por isso pode usar `COUNT`, `SUM`…).
```sql
-- cidades com mais de um cliente
SELECT cidade, COUNT(*) AS qtd
FROM clientes
WHERE cidade IS NOT NULL
GROUP BY cidade
HAVING COUNT(*) > 1;
```
A ordem em que o banco **executa** as partes: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. É por isso que um apelido criado no `SELECT` não pode ser usado no `WHERE`.

P: como combinar dados de duas tabelas
R: `JOIN` combina linhas de tabelas relacionadas. O `INNER JOIN` traz só as combinações que **casam** nos dois lados:
```sql
SELECT p.id AS pedido, p.data, c.nome AS cliente
FROM pedidos AS p
JOIN clientes AS c ON c.id = p.cliente_id
ORDER BY p.data;
```
- `p` e `c` são **apelidos** das tabelas: deixam a consulta curta e clara;
- `ON` diz como as linhas se ligam (a FK com a PK);
- `JOIN` sozinho é o mesmo que `INNER JOIN`.
Juntando três tabelas, o total de cada pedido:
```sql
SELECT p.id, c.nome, SUM(i.quantidade * i.preco_unit) AS total
FROM pedidos p
JOIN clientes c     ON c.id = p.cliente_id
JOIN itens_pedido i ON i.pedido_id = p.id
GROUP BY p.id, c.nome;
```

F: left-join
A: left join, junção à esquerda, sem correspondência
Q: diferente-de | o JOIN comum só traz linhas com par nas duas tabelas; o LEFT JOIN mantém todas as da esquerda | -> join
Q: consequencia | onde não há par, as colunas da direita vêm NULL | -> null
P: o que é left join
P: diferença entre inner join e left join
P: como listar clientes sem pedidos
P: como funciona o left join
P: left join
R: - `INNER JOIN`: só as linhas que têm par nos dois lados.
- `LEFT JOIN`: **todas** as linhas da tabela da esquerda; quando não há par, as colunas da direita vêm `NULL`.
```sql
SELECT c.nome, COUNT(p.id) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nome;
```
A Elisa aparece com 0 pedidos; com `INNER JOIN`, ela sumiria.
Para listar **só** quem não tem pedidos:
```sql
SELECT c.nome
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
WHERE p.id IS NULL;
```
Note o `COUNT(p.id)` e não `COUNT(*)`: o `*` contaria a linha com NULL como 1.

R: - **INNER JOIN:** só o que casa nos dois lados.
- **LEFT JOIN:** tudo da esquerda + o que casar da direita.
- **RIGHT JOIN:** tudo da direita + o que casar da esquerda (o mesmo que um LEFT com as tabelas trocadas).
- **FULL OUTER JOIN:** tudo dos dois lados, com NULL onde não há par.
- **CROSS JOIN:** todas as combinações possíveis (produto cartesiano): 5 clientes × 7 produtos = 35 linhas.
- **self join:** uma tabela com ela mesma (funcionário e seu chefe na mesma tabela).
O SQLite tem RIGHT e FULL desde a versão 3.39. A falha mais comum em JOIN é esquecer o `ON` ou errar a condição, o que multiplica linhas sem querer.

F: funcoes-texto
A: funções de texto, upper, lower, length, substr, trim, concatenar
Q: porque | os dados chegam escritos de jeitos diferentes, e essas funções padronizam o texto para comparar e exibir
Q: exemplo-de | um uso comum é comparar sem diferença de maiúsculas, com LOWER dentro do WHERE | -> where
P: o que são funções de texto em sql
P: como juntar textos em sql
P: como deixar texto maiúsculo em sql
R: No SQLite (outros bancos têm nomes parecidos):
```sql
SELECT UPPER(nome), LOWER(nome), LENGTH(nome) FROM clientes;
SELECT nome || ' (' || uf || ')' AS rotulo FROM clientes;   -- || concatena
SELECT SUBSTR(nome, 1, 3) FROM clientes;                    -- 3 primeiras letras
SELECT TRIM('  oi  '), REPLACE(nome, 'a', 'A') FROM clientes;

```
Em MySQL e SQL Server, use `CONCAT(a, b)`; PostgreSQL e Oracle aceitam `||`.

F: datas
A: datas, date, data, hora, strftime
Q: porque | o SQLite não tem um tipo próprio de data e guarda datas como texto no formato AAAA-MM-DD | -> tipos-dados
Q: consequencia | nesse formato, a ordem alfabética é a mesma ordem do tempo, então ORDER BY e comparações funcionam | -> order-by
P: como trabalhar com datas em sql
P: funções de data no sqlite
P: como filtrar por mês em sql
R: O SQLite guarda datas como texto ISO (`'2026-01-10'`), que ordena e compara certo:
```sql
SELECT date('now');                              -- hoje
SELECT date('now', '-7 days');                   -- uma semana atrás
SELECT date('2026-01-31', '+1 month');           -- soma meses
SELECT strftime('%Y-%m', data) AS mes, COUNT(*)  -- pedidos por mês
FROM pedidos GROUP BY mes;
SELECT * FROM pedidos WHERE data BETWEEN '2026-02-01' AND '2026-02-28';
SELECT julianday('2026-03-05') - julianday('2026-01-10');   -- dias entre datas
```
Outros bancos têm tipos de data de verdade e funções como `EXTRACT(MONTH FROM data)` (PostgreSQL), `DATEADD` (SQL Server) e `ADD_MONTHS` (Oracle).

F: case-when
A: case when, condição, se então, classificar
Q: porque | às vezes o resultado precisa mudar conforme o valor, como um "se" dentro da consulta
Q: diferente-de | o WHERE escolhe quais linhas aparecem; o CASE muda o que aparece em cada linha | -> where
P: como usar case when em sql
P: if dentro de select
R: `CASE` é o "se" do SQL, dentro de uma consulta:
```sql
SELECT nome, preco,
       CASE
           WHEN preco < 100  THEN 'barato'
           WHEN preco < 1000 THEN 'médio'
           ELSE 'caro'
       END AS faixa
FROM produtos;
```
Também serve para contar condições numa linha só:
```sql
SELECT COUNT(*) AS total,
       SUM(CASE WHEN status = 'entregue' THEN 1 ELSE 0 END) AS entregues
FROM pedidos;
```

F: importar-csv
A: csv, importar, exportar, planilha
Q: porque | é o jeito mais rápido de trazer os dados de uma planilha sem escrever um INSERT por linha | -> insert
Q: regra | com a tabela já criada, o --skip 1 pula a linha de cabeçalho do arquivo | -> create-table
P: como importar csv no sqlite
P: como exportar resultado para csv
R: No `sqlite3`:
```
.mode csv
.import --csv --skip 1 clientes.csv clientes
.headers on
.output relatorio.csv
SELECT * FROM clientes;
.output stdout
```
- `.import` carrega o CSV numa tabela (`--skip 1` pula a linha de cabeçalho se a tabela já existir);
- `.output arquivo` manda os resultados para o arquivo; `.output stdout` volta para a tela.
O DB Browser for SQLite faz o mesmo pelo menu Arquivo → Importar/Exportar.

F: sql-python
A: python, sqlite3, programa, script
Q: porque | o Python já traz o módulo sqlite3, então o mesmo banco funciona num programa sem instalar nada | -> comecar-sqlite
Q: regra | os valores vão por parâmetros (?) e nunca colados no texto do SQL, o que impede SQL injection
P: como usar sql no python
P: como usar sqlite3 no python
P: como conectar no banco pelo python
P: sqlite3 no python
P: python com banco de dados
R: O Python já traz o módulo `sqlite3`:
```python
import sqlite3

con = sqlite3.connect("loja.db")
con.row_factory = sqlite3.Row          # linhas acessíveis pelo nome da coluna

with con:                              # transação: commit no fim, rollback se der erro
    con.execute("INSERT INTO clientes (nome, cidade) VALUES (?, ?)",
                ("Gil Prado", "Manaus"))

for linha in con.execute("SELECT nome, cidade FROM clientes WHERE uf = ?", ("PE",)):
    print(linha["nome"], linha["cidade"])

con.close()
```
Os `?` são **parâmetros**: o valor nunca vira parte do comando, o que impede *SQL injection*. Nunca monte o SQL juntando textos com o que o usuário digitou. É exatamente assim que o Aprendiz conversa com o banco dele.

F: boas-praticas
A: boas práticas, dicas, erros comuns
Q: porque | consultas claras e previsíveis evitam o erro mais caro: alterar ou apagar o que não devia | -> delete
Q: regra | listar as colunas no SELECT, em vez de usar *, deixa claro o que a consulta usa | -> select
P: boas práticas de sql
P: como escrever sql legível
R: Hábitos que ajudam:
- palavras-chave em MAIÚSCULAS e uma cláusula por linha (`SELECT`, `FROM`, `WHERE`…);
- apelidos curtos e claros nas tabelas (`p` para pedidos, `c` para clientes);
- liste as colunas em vez de `SELECT *` no código;
- nomes de tabelas e colunas em `snake_case`, sem acento e sem espaço;
- sempre `ORDER BY` quando a ordem importa;
- confira com `SELECT` antes de `UPDATE`/`DELETE`, e use transações;
- parâmetros (`?`) para valores vindos de fora;
- comentários com `--` explicando regras de negócio.
