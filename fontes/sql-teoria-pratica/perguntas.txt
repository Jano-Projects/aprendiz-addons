P: o que é o modelo relacional de codd
P: teoria do modelo relacional
P: o que é uma relação na teoria de banco de dados
R: Em 1970, Edgar F. Codd (IBM) propôs tratar os dados como **relações** matemáticas. Os termos formais e seus equivalentes práticos:
- **relação** = tabela;
- **tupla** = linha;
- **atributo** = coluna;
- **domínio** = o conjunto de valores permitidos de um atributo (o tipo, mais as restrições);
- **grau** = número de atributos; **cardinalidade** = número de tuplas.
Na teoria, uma relação é um **conjunto**: não tem linhas repetidas nem ordem. O SQL relaxa isso (permite duplicados, por isso existe o `DISTINCT`, e a ordem vem do `ORDER BY`). A grande ideia de Codd foi a **independência de dados**: o programa diz *o que* quer, e o banco decide *como* guardar e buscar.

P: o que é álgebra relacional
P: quais as operações da álgebra relacional
P: o que é seleção projeção e junção
P: álgebra relacional
R: **Álgebra relacional** é o conjunto de operações sobre relações que está por trás de todo SQL:
- **seleção σ** (filtrar linhas) → `WHERE`;
- **projeção π** (escolher colunas) → a lista do `SELECT`;
- **produto cartesiano ×** → `CROSS JOIN`;
- **junção ⋈** (produto + seleção pela condição) → `JOIN ... ON`;
- **união ∪, interseção ∩, diferença −** → `UNION`, `INTERSECT`, `EXCEPT`;
- **renomeação ρ** → `AS`;
- **divisão ÷** ("quem se relaciona com **todos**") → não tem palavra própria em SQL; faz-se com `NOT EXISTS` duplo ou `GROUP BY ... HAVING COUNT`.
Exemplo: "nome dos clientes de PE" = π nome (σ uf='PE' (clientes)) = `SELECT nome FROM clientes WHERE uf = 'PE'`.
O otimizador do banco reescreve sua consulta usando as propriedades dessa álgebra (por exemplo, filtrar **antes** de juntar), por isso consultas escritas de jeitos diferentes podem ter o mesmo plano.

P: o que é divisão relacional
P: como achar quem comprou todos os produtos em sql
R: A **divisão** responde perguntas com "todos": quais clientes compraram **todos** os produtos de Móveis?
Jeito 1, com contagem:
```sql
SELECT p.cliente_id
FROM pedidos p
JOIN itens_pedido i ON i.pedido_id = p.id
JOIN produtos pr    ON pr.id = i.produto_id
WHERE pr.categoria = 'Móveis'
GROUP BY p.cliente_id
HAVING COUNT(DISTINCT pr.id) = (SELECT COUNT(*) FROM produtos WHERE categoria = 'Móveis');
```
Jeito 2, com `NOT EXISTS` duplo ("não existe produto de Móveis que ele não tenha comprado"):
```sql
SELECT c.id, c.nome FROM clientes c
WHERE NOT EXISTS (
    SELECT 1 FROM produtos pr
    WHERE pr.categoria = 'Móveis'
      AND NOT EXISTS (
          SELECT 1 FROM pedidos p JOIN itens_pedido i ON i.pedido_id = p.id
          WHERE p.cliente_id = c.id AND i.produto_id = pr.id
      )
);
```
No banco de exemplo, ninguém comprou os dois móveis (Cadeira e Mesa), então o resultado é vazio. Insira um item de Mesa no pedido 3 da Ana e rode de novo.

P: o que é dependência funcional
P: o que significa a determina b em banco de dados
R: Há uma **dependência funcional** A → B quando o valor de A **determina** o valor de B: duas linhas com o mesmo A têm sempre o mesmo B.
Exemplos:
- `cpf → nome` (o mesmo CPF é sempre da mesma pessoa);
- `cep → cidade`;
- `(pedido_id, produto_id) → quantidade`.
Uma **chave** é exatamente um conjunto de atributos que determina **todos** os outros. As formas normais são regras sobre quais dependências podem existir numa tabela: dependências "fora do lugar" significam dados repetidos e anomalias.

P: o que é anomalia de atualização inserção e exclusão
P: por que dados repetidos são um problema
R: Imagine uma tabela única `vendas(pedido, data, cliente, cidade_cliente, produto, preco_produto, quantidade)`. Ela sofre de três **anomalias**:
- **atualização:** o preço do Teclado aparece em cada venda. Mudou o preço do cadastro? Precisa alterar muitas linhas, e esquecer uma deixa o banco contraditório;
- **inserção:** não dá para cadastrar um produto novo que ainda não foi vendido (não há "venda" para ele);
- **exclusão:** apagar a única venda de um cliente apaga também o cadastro dele (nome e cidade).
A solução é **decompor** em tabelas menores (`clientes`, `produtos`, `pedidos`, `itens_pedido`) em que cada fato aparece uma vez só. É o que as formas normais guiam.

P: o que é 1fn em detalhes
P: exemplo de primeira forma normal
P: primeira forma normal na prática
P: 1fn
R: **1FN:** todo atributo é **atômico** (um valor só) e não há grupos repetidos.
Fora da 1FN:
```
clientes(id, nome, telefones)            telefones = '9999-1111, 9888-2222'
clientes(id, nome, tel1, tel2, tel3)     grupo repetido
```
Problemas: não dá para buscar por um telefone com `=`, nem garantir o formato, e um quarto telefone não cabe.
Na 1FN:
```sql
CREATE TABLE telefones (
    cliente_id INTEGER REFERENCES clientes(id),
    numero     TEXT,
    PRIMARY KEY (cliente_id, numero)
);
```
"Atômico" depende do uso: uma data é atômica para a maioria dos sistemas, mesmo tendo dia, mês e ano.

P: o que é 2fn em detalhes
P: exemplo de segunda forma normal
P: o que é dependência parcial
P: segunda forma normal
P: 2fn
R: **2FN:** está na 1FN e **nenhum atributo depende só de parte de uma chave composta** (sem dependência parcial).
Fora da 2FN, com chave (`pedido_id`, `produto_id`):
```
itens_pedido(pedido_id, produto_id, quantidade, nome_produto, categoria)
```
`nome_produto` e `categoria` dependem só de `produto_id`, não da chave inteira. Resultado: o nome do produto se repete em cada item vendido.
Na 2FN: tire o que depende só de `produto_id` para a tabela `produtos`, e deixe em `itens_pedido` só o que depende do par (`quantidade`, `preco_unit`).
Tabelas com chave de uma coluna só já estão automaticamente na 2FN (se estiverem na 1FN).

P: o que é 3fn em detalhes
P: exemplo de terceira forma normal
P: o que é dependência transitiva
P: explica a terceira forma normal
P: terceira forma normal
P: 3fn
R: **3FN:** está na 2FN e **nenhum atributo não-chave depende de outro atributo não-chave** (sem dependência transitiva: chave → A → B).
Fora da 3FN:
```
clientes(id, nome, cep, cidade, uf)
```
`id → cep` e `cep → cidade, uf`. A cidade depende da chave só **através** do CEP. Se a cidade de um CEP mudar de nome, é preciso atualizar todos os clientes daquele CEP.
Na 3FN: `ceps(cep, cidade, uf)` e `clientes(id, nome, cep)`.
Na prática, muitos sistemas mantêm cidade e UF no cliente por simplicidade (desnormalização consciente). Saber a regra ajuda a decidir quando quebrá-la.

P: o que é forma normal de boyce codd
P: o que é bcnf
P: o que é 4fn e 5fn
R: **BCNF** (Forma Normal de Boyce-Codd) é uma 3FN mais rigorosa: **todo determinante é uma chave candidata**. Só difere da 3FN em casos com várias chaves candidatas sobrepostas.
Exemplo: `aulas(aluno, disciplina, professor)`, em que cada professor dá uma só disciplina (`professor → disciplina`) e a chave é (aluno, disciplina). Está na 3FN, mas `professor` determina `disciplina` sem ser chave. Em BCNF: `professores(professor, disciplina)` e `matriculas(aluno, professor)`.
- **4FN:** sem dependências multivaloradas independentes na mesma tabela (os idiomas e os hobbies de uma pessoa não devem ficar na mesma tabela, gerando todas as combinações).
- **5FN:** a tabela não pode ser decomposta em menores sem perder informação.
Na prática, chegar à 3FN/BCNF resolve quase todos os casos reais.

P: o que é decomposição sem perda
R: Ao dividir uma tabela em duas para normalizar, a **junção** das duas precisa devolver exatamente a original: nem menos linhas, nem linhas a mais ("espúrias").
A decomposição de R em R1 e R2 é **sem perda** quando os atributos em comum formam uma **chave** de R1 ou de R2.
Exemplo: `clientes(id, nome, cep, cidade)` → `clientes(id, nome, cep)` + `ceps(cep, cidade)`. Em comum: `cep`, que é chave de `ceps`. A junção pelo CEP reconstrói tudo. Dividir por `cidade` (em comum) não seria sem perda: duas cidades com o mesmo nome em estados diferentes gerariam combinações falsas.

P: o que são os níveis de isolamento de transação
P: o que é read committed e serializable
P: o que é leitura suja leitura não repetível e fantasma
P: níveis de isolamento
P: isolamento de transação
R: Quando transações rodam ao mesmo tempo, três **anomalias** podem aparecer:
- **leitura suja:** ler um dado alterado por outra transação que ainda não deu COMMIT (e que pode ser desfeito);
- **leitura não repetível:** ler a mesma linha duas vezes e ver valores diferentes, porque outra transação alterou no meio;
- **fantasma:** repetir uma consulta e aparecerem linhas novas que outra transação inseriu.
Os **níveis de isolamento** do padrão SQL, do mais fraco ao mais forte:
- **READ UNCOMMITTED:** permite as três;
- **READ COMMITTED:** evita leitura suja (padrão do PostgreSQL, Oracle e SQL Server);
- **REPEATABLE READ:** evita também a não repetível (padrão do MySQL/InnoDB);
- **SERIALIZABLE:** o resultado é como se as transações rodassem uma de cada vez.
Mais isolamento = mais segurança e menos concorrência. O SQLite, com uma escrita por vez, se comporta como serializable.

P: o que é mvcc
P: como o banco lida com acessos simultâneos
P: o que é lock em banco de dados
R: Há duas estratégias para várias transações ao mesmo tempo:
- **travas (locks):** quem vai alterar uma linha a trava; os outros esperam. Simples, mas leituras e escritas se bloqueiam.
- **MVCC** (controle de concorrência multiversão): cada alteração cria uma **nova versão** da linha; cada transação enxerga um "retrato" consistente do momento em que começou. **Leitores não bloqueiam escritores e vice-versa.** É o que fazem PostgreSQL, Oracle e MySQL (InnoDB).
O SQLite no modo **WAL** (o Aprendiz liga com `PRAGMA journal_mode = WAL`) faz algo parecido: as leituras continuam enquanto alguém escreve. O risco das travas é o **deadlock** (duas transações esperando uma pela outra); o banco detecta e cancela uma delas.

P: como funciona o log de transações
P: o que é write ahead log
P: como o banco garante a durabilidade
R: Para garantir a **durabilidade** (o D do ACID) sem gravar cada página da tabela no disco a cada COMMIT, os bancos usam um **log**:
1. a alteração é escrita primeiro, em sequência, num arquivo de log (**WAL**, *write-ahead log*), e o log é forçado ao disco (`fsync`);
2. só então o COMMIT é confirmado;
3. as páginas das tabelas são atualizadas depois, com calma (**checkpoint**).
Se a energia cair, ao reabrir o banco **refaz** o que estava no log e confirmado, e **descarta** o que não foi confirmado. Escrever em sequência no log é muito mais rápido que pular pelo disco atualizando páginas.
No SQLite em modo WAL, você vê o arquivo `banco.db-wal` ao lado do banco.

P: como funciona o índice b-tree por dentro
P: por que o índice deixa a busca rápida
R: Um índice **B+tree** guarda as chaves ordenadas numa árvore larga e baixa:
- cada **nó** ocupa uma página do disco (4 KB no SQLite) e guarda centenas de chaves;
- os **nós internos** só guiam a busca ("chaves menores que 500, vá para a esquerda");
- as **folhas** têm as chaves e o endereço da linha (ou a própria linha), e são ligadas em sequência.
Com 300 chaves por nó, 3 níveis já indexam 300³ = 27 milhões de linhas: achar uma é ler 3 ou 4 páginas, em vez de milhões.
Como as folhas estão ligadas em ordem, o índice também acelera **faixas** (`BETWEEN`, `>`), `ORDER BY` e `MIN`/`MAX`. Ao inserir, um nó cheio se divide em dois e a árvore se mantém equilibrada sozinha.
No SQLite, a própria tabela é uma B-tree ordenada pelo `rowid`, por isso buscar pela `INTEGER PRIMARY KEY` é tão rápido.

P: como o otimizador de consultas funciona
P: o que é plano de execução por dentro
R: Quando você manda uma consulta, o banco:
1. **analisa** o texto e confere tabelas e colunas;
2. **reescreve** usando a álgebra relacional (empurra filtros para antes das junções, transforma subconsultas em junções);
3. **gera planos** alternativos: em que ordem juntar as tabelas, com que algoritmo (laços aninhados, hash join, merge join), usando qual índice;
4. **estima o custo** de cada plano com **estatísticas** (quantas linhas tem cada tabela, quantos valores distintos tem cada coluna);
5. **executa** o mais barato.
Por isso estatísticas desatualizadas levam a planos ruins (rode `ANALYZE` depois de grandes cargas), e por isso vale olhar o plano em vez de adivinhar.

P: quais os algoritmos de join
P: o que é nested loop hash join e merge join
R: O banco tem três jeitos principais de juntar duas tabelas:
- **laços aninhados (nested loop):** para cada linha de A, procura as de B. Ótimo quando A é pequena e B tem **índice** na coluna da junção. É o que o SQLite usa.
- **hash join:** monta uma tabela hash com a menor tabela e percorre a maior consultando a hash. Ótimo para tabelas grandes sem índice, com `=`.
- **merge join:** com as duas já ordenadas pela coluna da junção, percorre as duas em paralelo, como intercalar duas listas. Ótimo quando já existem índices ordenados.
O otimizador escolhe sozinho; você influencia criando os índices certos e mantendo as estatísticas em dia.

P: o que é teorema cap
P: o que é consistência eventual
R: Em bancos **distribuídos** (vários servidores), o **teorema CAP** diz que, quando a rede entre eles falha (**P**artição), é preciso escolher entre:
- **C**onsistência: todos veem o mesmo dado; para isso, alguns pedidos esperam ou falham;
- **A** (disponibilidade): todos respondem sempre, mesmo que com dados um pouco desatualizados.
**Consistência eventual** é a escolha pela disponibilidade: as cópias podem divergir por um tempo, mas convergem depois (o contador de curtidas que demora a bater em todo lugar).
Um banco relacional num servidor só (ou o SQLite do Aprendiz) não sofre esse dilema: é consistente por natureza.

P: como modelar um banco de dados na prática
P: exemplo de modelagem de banco de dados passo a passo
R: Exemplo: um sistema de **biblioteca**.
1. **Requisitos:** "leitores pegam livros emprestados; um livro tem vários exemplares; um livro pode ter vários autores".
2. **Entidades:** Leitor, Livro, Exemplar, Autor, Empréstimo.
3. **Relacionamentos:** Livro 1:N Exemplar; Livro N:N Autor; Leitor 1:N Empréstimo; Exemplar 1:N Empréstimo.
4. **Tabelas:**
```sql
CREATE TABLE leitores (id INTEGER PRIMARY KEY, nome TEXT NOT NULL, email TEXT UNIQUE);
CREATE TABLE livros   (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL, isbn TEXT UNIQUE, ano INTEGER);
CREATE TABLE autores  (id INTEGER PRIMARY KEY, nome TEXT NOT NULL);
CREATE TABLE livro_autor (
    livro_id INTEGER REFERENCES livros(id),
    autor_id INTEGER REFERENCES autores(id),
    PRIMARY KEY (livro_id, autor_id)
);
CREATE TABLE exemplares (id INTEGER PRIMARY KEY, livro_id INTEGER NOT NULL REFERENCES livros(id));
CREATE TABLE emprestimos (
    id          INTEGER PRIMARY KEY,
    exemplar_id INTEGER NOT NULL REFERENCES exemplares(id),
    leitor_id   INTEGER NOT NULL REFERENCES leitores(id),
    retirado_em TEXT NOT NULL,
    devolvido_em TEXT,
    CHECK (devolvido_em IS NULL OR devolvido_em >= retirado_em)
);
CREATE INDEX idx_emp_leitor ON emprestimos (leitor_id);
```
5. **Conferir as formas normais** e as consultas mais importantes ("quais exemplares estão emprestados?" → `WHERE devolvido_em IS NULL`).

```sql
-- 1. o produto mais caro de cada categoria

           ROW_NUMBER() OVER (PARTITION BY categoria ORDER BY preco DESC) AS rn
    FROM produtos
)

-- Caneca (Cozinha) · Monitor (Informática) · Mesa (Móveis)

    FROM itens_pedido GROUP BY pedido_id

SELECT c.nome, SUM(t.total) AS gasto
FROM pedidos p
JOIN totais t   ON t.pedido_id = p.id
JOIN clientes c ON c.id = p.cliente_id
WHERE p.status = 'entregue'
GROUP BY c.id, c.nome
ORDER BY gasto DESC;
-- Bruno Lima 1940 · Ana Souza 930
```

```sql
SELECT * FROM pedidos WHERE status = 'aberto' ORDER BY data;   -- SCAN pedidos + USE TEMP B-TREE

CREATE INDEX idx_pedidos_status_data ON pedidos (status, data);
```

No 9, o índice composto (`status`, `data`) resolve o filtro **e** a ordenação: dentro de cada status, as datas já estão em ordem no índice, e o "TEMP B-TREE" (ordenação extra) some do plano. Para um UPDATE também ser barrado, crie um segundo trigger `BEFORE UPDATE`.
